# P2.2 handoff: Unified Library and Favorites

**Status:** implemented in the working tree on `dev`, based on `75d9471`. Nothing is staged, committed, pushed, deployed or migrated. Full design: [../personal-library.md](../personal-library.md#favorites-p22).

**Verdict: READY WITH NONBLOCKING LIMITATIONS.** Every automated check passes. Signed-in behavior has been tested with component and isolated database tests, but **not yet in a real browser with a real session**. That check needs live services and is deferred to the owner, as approved.

## What exists

- One Library: All Songs at `/library` (public, cached) and Favorites at `/library/favorites` (approved members). The navbar is unchanged. Future sections are hidden.
- A heart on Library rows, song pages and the Favorites section.
- Favorites with collection-wide search, three sorts, paging, and distinct states for unavailable, ambiguous and temporarily unknown songs.
- One Dashboard link beside "Your profile", with no new query.

## Subcheckpoints

### P2.2A: Legacy catalog

- **Defect:** a module-level map kept each environment's first successful copy forever, so a row an older deployment wrote later was invisible until a restart.
- **Reproduced** on isolated PGlite: the catalog returned 2 songs where the test expected 3.
- **Fix:** each environment runs one copy at a time plus one trailing copy. A caller arriving during a copy waits for the next one, and nothing is remembered once copies finish.
- Two unit tests that required the defect were corrected, as approved. Their SQL-shape and atomicity assertions are unchanged.
- A `NOT EXISTS` pre-filter was tried and removed because it measured slower at 1,000 rows.
- The public catalog cache (up to 24 hours) is unchanged, as approved. The Personal Library sees late rows at once.

### P2.2B: Server contracts

- Three endpoints under `/api/account/favorites`, all through `withPersonalLibrary`, private and no-store.
- **Erasure:** `removeFavorite`, `clearRecent`, `deleteNote` and the pruning in `recordRecent` now check the marker inside their locked statement. The pruning gap was found during this work. Favorites reads check it in the same statement.
- **Identity:** an alias claimed by another song no longer enters a song's mutation scope. This was a real wrong-delete risk in the P2.1 resolver.
- **Case safety:** one ASCII-only fold is shared by the resolver and SQL. Colliding canonical IDs are `ambiguous`, never merged. Exact removal stays case-sensitive with no alias expansion.

### P2.2C: Unified Library

- `app/library/layout.tsx` mounts a client provider and reads no session.
- `/library/favorites` is in `MEMBER_SECTIONS`, the proxy matcher and `robots.ts`, and checks the session on the page itself.
- The service worker has no fetch handler and caches nothing, so it needed no change.

### P2.2D: Favorites experience

An account-scoped controller, using React primitives only, handles optimistic updates, one request per song, latest-intent coalescing, cross-tab signals and focus or navigation refresh.

**While an outcome is uncertain:**

| Event | What happens |
|---|---|
| Timeout, lost response or generic server failure | The song becomes uncertain, and one read runs |
| That read answers | Updates what was last observed; stays uncertain |
| Ordinary click, either direction | Sends nothing |
| Time passes | Nothing is retried, and there is no polling |
| Member picks Add or Remove | Sends exactly one request |
| Original request gets a definite answer | Uncertainty ends |
| Original answers after the member's choice | The song is read again and shows the server's state |
| Account changes | Everything is discarded; the server refuses a mismatched account |

## Known limitations

- After an explicit choice on an uncertain song, a still-travelling earlier request can land later. The tab corrects itself on that request's answer or the next refresh. This is inherent in the approved server-ordered model.
- Exact last-click-wins across devices is not promised.
- `loadNote` and `listRecent` still return data under an erasure marker. No route reaches them. **P2.3 and P2.4 must refuse a marked account before exposing them.**
- The public catalog can show a late legacy row up to 24 hours after the Personal Library does.
- A song known only from history cannot be newly favorited (accepted in P2.1).
- PGlite does not reproduce multi-connection lock contention.
